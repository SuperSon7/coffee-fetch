# 스택 브리프 — 개인 기술 소식 브리핑 설계 보고서

작성·조사일: 2026-09-15. 범위: 제품 설계, 참고자료 조사, 화면 목업. 서비스 구현·배포·예약 작업 생성은 하지 않았다. 참고 서비스 조사와 수집 방식 조사는 에이전트 2개가 나누어 진행했다.

## 1. 제안하는 도구

**IT·DevOps·Cloud·AI·Observability의 새 소식을 모으고, Kubernetes·Grafana·Python 등 관심 도구에 관련된 변화를 아침 5분 분량으로 보여주는 개인 웹 브리핑 도구.** 가칭은 ‘스택 브리프’다.

목표는 ‘지난 브리핑 이후 무엇이 바뀌었고, 내 업무와 왜 관련 있는지’를 한 화면에서 판단하는 것이다. 한국어로 요약하되 제품명·버전·API 이름은 원문을 유지한다.

### 추천 기본값 — 아직 확정하지 않은 설계 제안

| 항목 | 제안 |
|---|---|
| 관심 분야 | IT, DevOps, Cloud, AI, Observability |
| 우선 도구 | Kubernetes, Grafana, Python |
| 연관 도구 후보 | Prometheus, OpenTelemetry, Loki, Helm, Terraform, Argo CD. 자동 구독하지 않고 선택 후보로 제시 |
| 발행 | 평일 오전 08:00, Asia/Seoul |
| 대안 주기 | 매일, 6시간마다, 특정 요일, 주간 회고 |
| 분량 | 기본 5분, 3분·10분 선택; 중요한 변화가 적으면 짧게 종료 |
| 전달 | 웹 브리핑을 기본으로 하고 이메일 요약은 선택 기능 |
| 수집 | 초기에는 1~3시간 간격을 검토하되 소스별 제한에 맞춤 |
| 사용 환경 | 버전·클라우드 사업자·리전·Grafana Cloud/자체 운영 여부를 선택 입력 |

현재 실제 사용 버전과 클라우드 사업자는 알 수 없다. 따라서 ‘관심 도구 일치’와 ‘내 환경에 영향 있음’을 구분해야 한다.

기존 제품도 요약과 정기 브리핑을 제공한다. 직접 만드는 가치는 **도구·버전·운영 환경 중심의 우선순위와 이전 회차 대비 변화**에 있다.

|---|---|---|
| Feedly | 본문 유사도 기반 중복 제거, 주제 제외 | 같은 발표를 하나로 묶고 ‘이 주제 줄이기’ 제공. [중복 제거 문서](https://docs.feedly.com/article/218-how-does-deduplication-work) |
| Inoreader | 예약 이메일 다이제스트와 AI 요약. 해당 다이제스트는 Team/Custom 플랜에 포함 | 주기 설정과 발행 미리보기 분리. [공식 안내](https://www.inoreader.com/blog/2025/08/redesigned-email-digests-for-more-control-and-flexibility.html) |

## 3. 무엇을 수집할 것인가

### 출처 우선순위

1. 공식 릴리스·지원 정책·보안 공지: 버전, 호환성, 지원 종료처럼 판단의 근거가 되는 자료.
2. 공식 블로그·기술 문서: 사용법과 새로운 기능의 맥락.
3. 신뢰할 만한 해설·커뮤니티: 활용 사례와 발견. 성능 주장과 의견은 검증된 사실로 표현하지 않는다.

## 4. 수집에서 브리핑까지

`관심 프로필 → 소스 수집 → 문서 정리 → 같은 사건 묶기 → 관련성 판정 → 근거 있는 한국어 요약 → 회차 저장 → 웹 표시/선택 알림`

### 수집과 발행의 분리

수집은 소스별 주기로 돌고, 발행은 사용자 일정에 맞춘다. 08:00 발행이라면 그 이전에 확보한 자료로 회차를 확정하고 늦게 발견한 자료는 다음 회차에 포함한다. 화면에 대상 기간과 확인 시각을 표시한다.

‘지난 24시간’ 검색만 반복하지 않고 소스별 마지막 성공 수집 위치를 저장한다. 장애가 나면 그 지점 이후를 다시 수집한다. 같은 회차 키로 중복 발행을 막고, 늦게 실행된 작업은 미완료 회차 한 번만 보완한다. 정기 실행의 시간대와 재시작 처리는 별도 검증한다. n8n은 시간대 설정을 사용하며 누락 실행 보완 기능에는 버전·스케줄러 조건이 있다. [Schedule Trigger 문서](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.scheduletrigger)

### 중복과 업데이트 처리

- 같은 문서: 소스 ID, 정규화한 URL, 내용 지문으로 중복 제거.
- 같은 사건: 도구명·버전·발표 내용을 비교해 공식 발표, 해설, 토론을 한 카드로 묶기.
- 후속 변화: 신규 버전, 정정, 정식 출시 전환은 기존 소식과 연결하되 변경점만 새 회차에 표시.
- 날짜: 원문 게시일·수정일·최초 발견일을 따로 저장. 게시일이 없으면 ‘게시일 미확인 · 오늘 발견’으로 표시.

GitHub에서는 releases 목록으로 시험판 여부와 게시 시각을 확인한다. `/latest` 하나만 조회하면 전체 새 릴리스를 포괄하지 못한다. [GitHub Releases API](https://docs.github.com/en/rest/releases/releases)

### 우선순위 — 초기에는 설명 가능한 규칙

| 순서 | 조건 | 화면 표현 |
|---|---|---|
| 먼저 확인 | 관심 도구의 보안·지원 종료·호환성 변경. 환경 일치 여부 별도 확인 | ‘영향 확인 필요’ 또는 근거가 있을 때 ‘사용 버전 해당’ |
| 주요 업데이트 | 관심 도구의 정식 기능·운영 개선 | 무엇이 바뀌었는지 한 줄 |
| 더 알아보기 | 해설, 활용 사례, AI·클라우드 동향 | 관심사와 관련 있는 이유 |
| 발견 | 새 도구, 커뮤니티 제안 | 검증 상태와 소개 출처 |

인기 점수를 최우선으로 두지 않는다. 같은 분야가 회차 전체를 차지하지 않게 분야별 상한을 두되, 중요한 운영 변경은 그 상한의 예외로 둔다. 숫자로 된 가짜 신뢰 점수 대신 ‘공식 발표 / 커뮤니티 소개 / 원문 미확보’를 보여준다.

### 요약 규격

- 기본: 한 줄 제목 + 2문장 변화 요약 + 내게 중요한 이유 + 원문 링크.
- 상세: 해당 버전·환경, 시행일, 이전 회차와 차이, 관련 근거.
- 사실과 해석 분리. 버전·날짜·지원 범위는 근거 문서와 대조.
- 본문 확보 실패 시 추측 요약을 만들지 않고 제목·링크와 확인 상태만 표시.
- 문서 내 지시문은 수집 자료로만 취급. 요약 과정에서 외부 작업을 실행하지 않음.

## 5. 보기 편한 UI 구성

### 홈: 읽기 중심의 2단 화면

왼쪽에는 오늘·지난 브리핑·저장함과 관심 목록을 배치한다. 본문은 날짜 → 오늘 핵심 → 3/5/10분 분량 → 소식 카드 순서다. 넓은 화면에서도 복잡한 3단 대시보드는 피하고 상세는 해당 카드 아래 펼친다.

카드는 `변화 유형·도구 → 제목 → 요약 → 선정 이유 → 근거 펼치기 → 저장/관심 조절` 순서다. 원문 출처와 날짜는 기본 상태에서도 보인다. ‘새 소식 238건’ 같은 미열람 숫자보다 오늘 읽을 회차를 강조한다.

모바일에서는 왼쪽 메뉴를 접고 카드 한 열로 읽는다. 최종 제품에서는 접힌 메뉴를 여는 버튼과 관심 주제 접근을 제공한다. 목업은 핵심 읽기 화면만 표현한다.

### 다른 화면의 역할

| 화면 | 구성 |
|---|---|
| 관심 설정 | 분야, 도구, 중요도, 선택적인 버전·클라우드 환경, 제외 키워드 |
| 주기 및 알림 | 요일·시각·시간대, 분량, 웹/이메일, 다음 발행 미리보기 |
| 지난 브리핑 | 회차별 목록, 대상 기간, 후속 정정 표시 |
| 저장함 | 저장한 소식, 도구별 태그, 메모 |
| 소스 관리 | URL, 출처 종류, 마지막 성공 시각, 오류·일시정지 |

### 꼭 필요한 상태

- 새 소식 없음: 짧은 완료 상태. 알림은 기본 생략.
- 수집 일부 실패: 확인한 범위와 실패 소스를 표시. ‘변화 없음’으로 오인하지 않도록 분리.
- 첫 사용: 추천 소스 선택 후 첫 브리핑 미리보기. 소스를 임의 확정하지 않음.
- 환경 정보 부족: 관련성은 표시하되 실제 영향은 ‘확인 필요’.
- 후속 정정: 이전 회차에도 정정 표시, 새 회차에는 변경 요약.

목업의 제목·시각·수집 건수는 가상 데이터다. 3/5/10분 전환, 근거 펼치기, 저장 상태만 로컬에서 체험할 수 있다. 일정·수집·실제 저장 기능을 구현한 것은 아니다.

## 6. 구현 방식에 대한 설계 권고

| 접근 | 장점 | 부담 | 적합성 |
|---|---|---|---|
| 기존 리더 + 정기 다이제스트 | 빠르게 읽기 습관과 소스 품질 검증 | 환경별 영향 판정과 UI 제약 | 사전 검증에 적합 |
| 자동화 워크플로 + 간단한 읽기 화면 | 수집·요약 흐름을 작은 규모로 시험 | 사건 묶기·회차 기록이 복잡해지면 관리 부담 | 초기 실험의 대안 |
| 맞춤 웹 도구 | 버전·근거·회차·개인화 UI 통제 | 수집기 운영과 품질 관리 필요 | 최종 방향으로 추천 |

권장 구조는 **Python 수집·요약 작업 + 데이터 저장소 + 반응형 웹 화면 + 예약 실행기**다. 구체 라이브러리는 구현 단계에서 선정한다. 처음에는 단일 사용자와 단일 배포 단위로 시작하고, 이미 관리하는 환경이 없다면 이 도구만을 위해 Kubernetes 클러스터를 도입할 필요는 없다.

보관할 핵심 자료: 관심 프로필, 소스 설정과 수집 상태, 원문 메타데이터, 사건 묶음, 근거별 요약, 발행 회차, 저장·관심 피드백. 간단한 규칙으로 시작하고 임베딩 검색·추천 학습은 실제 중복과 오분류가 확인될 때 추가한다.

비용은 소스 수·후보 기사 수·원문 길이·요약 빈도·선택 모델에 좌우된다. 현재 월 비용을 확정할 근거는 없다. 먼저 중복 제거와 관련성 필터를 적용한 뒤 선별된 자료만 요약하고, 문서 내용이 바뀌지 않으면 기존 결과를 재사용한다.

## 7. 첫 버전의 범위와 판단 기준

**첫 버전:** 관심 분야/도구, 공식 RSS·릴리스 수집, 중복 묶기, 출처 있는 한국어 요약, 정기 회차 생성, 3/5/10분 읽기, 저장, 수집 실패 표시.

**후속:** 이메일 전달, 버전별 영향 정밀화, 주간 회고, 새 소스 발견, 관심 피드백 학습. 실시간 장애 모니터링이나 자동 업그레이드는 별도 제품 범위다.

구현 이후에는 1~2주 동안 후보 기사 30~50건을 직접 검토해 관련성, 중복 묶기, 요약 사실성을 확인한다. 이는 제안하는 검증 계획이며 이번에 실행한 결과가 아니다.

- 반복 실행·실패 후 복구에도 같은 회차가 중복 발행되지 않는가?
