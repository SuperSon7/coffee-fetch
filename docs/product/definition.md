# Coffee Fetch — 현재 제품 정의

## 목적

관심 기술의 새 소식을 부담 없는 양으로 읽습니다. 개인적인 재미를 위해 만들고, 만드는 과정에서 AI를 어떻게 활용할지 배웁니다. 별도의 학습 목표 개수나 일정은 강제하지 않습니다.

관심 분야는 IT·DevOps·Cloud·AI·Observability, 관심 도구는 Kubernetes·Grafana·Python 등입니다. 기본 사용에 고민 입력은 필요하지 않습니다.

## 첫 버전 범위

| 구분 | 내용 |
|---|---|
| 초기 설정 | 관심 분야·도구, 받을 주기, 읽을 분량 |
| 화면 | 짧은 요약 카드와 원문 링크 |
| 행동 | 원문 열기, 명시적 읽음 표시, 나중에 보기 |
| 기록 | 지난 브리핑과 저장한 소식 |
| 보류 | 고민 기반 추천, 저녁 회고, 학습·복습 기능, 관심 줄이기 |

## 화면과 동작

2026-09-23 대화에서 검토한 목업을 첫 버전의 작업 기준으로 사용합니다. 화면 배치·스타일·메뉴 구성은 변경 가능한 초안입니다. 아래 동작을 유지하면서 화면 구성을 바꿀 수 있습니다. 목업 소식은 가상 예시이며 실제 수집·요약 품질을 검증한 결과는 아닙니다.

### 1. 브리핑

| 요소·행동 | 표시·동작 |
|---|---|
| 브리핑 열기 | 오늘 브리핑의 소식 목록을 표시 |
| 소식 카드 | 제목, 짧은 요약, 출처, 원문 링크, 게시일, 자료 유형, 관련 기술, 읽기·저장 상태 |
| 원문 열기 | 외부 원문을 새 탭으로 열고 ‘안 읽음’을 ‘읽는 중’으로 변경. 이미 읽은 소식은 읽음 유지 |
| 읽음 표시 | 사용자가 다 읽었다고 판단한 뒤 직접 ‘읽음’으로 표시 |
| 읽음 취소 | 실수로 표시했다면 ‘읽는 중’으로 되돌림 |
| 나중에 보기 | 소식을 저장하거나 저장 해제. 읽기 상태와 독립적으로 동작 |
| 날짜 선택 | 오늘 이전 날짜의 브리핑을 당시 목록·순서·요약 그대로 표시 |

외부 원문의 스크롤이나 완독 여부는 자동 판정하지 않습니다. 지난 브리핑의 내용은 유지하되 읽음·저장은 현재 상태를 표시합니다. 동일 소식은 어느 화면에서 열어도 동일한 읽기·저장 상태를 사용합니다.

### 2. 나중에 보기

| 요소·행동 | 표시·동작 |
|---|---|
| 저장 목록 | 저장한 소식을 다시 찾고 원문 열기·읽음 표시 가능 |
| 보관 | 사용자가 저장을 해제하기 전까지 유지. 읽음 처리나 관심사 변경으로 제거하지 않음 |
| 저장 해제 | 저장 목록에서 제외. 원래 브리핑이나 읽음 상태는 유지 |
| 빈 목록 | 저장된 소식이 없음을 표시하고 브리핑으로 이동 가능 |

### 3. 관심사·설정

| 요소·행동 | 표시·동작 |
|---|---|
| 관심 분야·도구 | 받고 싶은 분야와 도구 선택. 최소 하나 필요 |
| 받을 주기·시각 | 브리핑 생성 주기와 시각 설정 |
| 읽을 분량 | 브리핑당 최대 소식 수 설정. 부족한 소식을 억지로 채우지 않음 |
| 다음 브리핑부터 적용 | 변경을 저장하고 현재 브리핑은 유지. 다음 생성부터 새 설정 사용 |
| 지금 적용 | 변경한 관심사로 오늘 브리핑을 새로 구성. 지난 날짜의 브리핑과 저장한 소식 유지 |

목업의 매일 07:00·최대 3개는 예시이며 기본값 확정이 아닙니다. 즉시 적용은 현재 검토안대로 오늘 브리핑 재구성으로 해석합니다. 생성 과정의 세부 규칙은 아래 미결정 항목에서 다룹니다.

### 처리 중·빈 결과·실패

다음은 구현 시 사용할 기본 동작안입니다. 목업에서는 모든 상태를 재현하지 않았습니다.

- 생성 중: 처리 중임을 표시하고 같은 요청의 중복 실행 방지. 기존 브리핑은 계속 읽을 수 있게 유지.
- 새 소식 없음: 정상 처리 결과가 비어 있음을 표시.
- 수집·요약 실패: 새 소식 없음과 구분하고 재시도 가능하게 표시. 기존 브리핑은 유지.
- 상태 저장 실패: 읽음·저장이 완료된 것처럼 표시하지 않고 실패와 재시도 안내.

## 기능에서 도출한 기본 데이터

아래는 기능에 필요한 정보와 관계입니다. DB 제품·테이블·컬럼·API를 확정한 설계는 아닙니다.

| 개념 | 필요한 정보 | 필요한 이유 |
|---|---|---|
| 설정 | 관심 분야·도구, 생성 주기·시각·시간대, 최대 소식 수 | 무엇을 언제 얼마나 제공할지 결정 |
| 소식 | 식별자, 원문 주소, 제목, 출처, 게시일, 자료 유형, 관련 기술 | 원문 식별과 카드 표시 |
| 브리핑 | 식별자, 대상 날짜, 생성 시각, 생성에 사용한 설정 | 같은 날짜의 생성 결과와 당시 기준 구분 |
| 브리핑 항목 | 브리핑과 소식의 연결, 표시 순서, 당시 제목·요약·출처·게시일·유형·기술·원문 주소 | 이후 소식 정보가 바뀌어도 지난 브리핑 내용을 유지 |
| 읽기·저장 상태 | 소식 식별자, 안 읽음·읽는 중·읽음, 저장 여부 | 화면을 바꿔도 상태 유지. 읽기와 보관을 별개로 관리 |

관계: 브리핑 하나에 여러 항목이 들어가고, 각 항목은 소식 하나를 가리킵니다. 같은 소식이 여러 브리핑에 포함되어도 읽기·저장 상태는 공유합니다. 저장한 소식은 브리핑을 새로 구성해도 접근할 수 있어야 합니다. 개인용 첫 버전에서 로그인·다중 사용자 기능은 추가하지 않습니다.

## 동작 확인 기준

- 처음 원문을 열면 읽는 중으로 바뀌고, 직접 표시해야 읽음이 된다. 다시 열어도 읽음은 유지된다.
- 저장 후 읽음 표시·관심사 변경·오늘 브리핑 재구성을 해도 저장 목록에 남는다. 해제하면 저장 목록에서만 빠진다.
- 관심사 변경을 다음 회차에 적용하면 오늘 내용은 그대로다. 즉시 적용하면 오늘 내용만 새로 구성한다.
- 지난 날짜의 카드 내용·순서는 유지되고, 같은 소식의 읽음·저장 변경은 모든 화면에 반영된다.
- 생성 실패와 정상 처리 후 새 소식 없음이 구분된다. 실패 때문에 기존 브리핑이 사라지지 않는다.

## 유지할 원칙

- 원문을 전부 보여주기보다 짧은 요약과 링크로 읽을지 판단하게 합니다.
- 소스가 많아져도 읽을 분량을 불필요하게 늘리지 않습니다.
- 행사 발표는 수집 후보입니다. 소개만 확보했으면 발표 전체를 요약한 것처럼 쓰지 않습니다.
- 사용 버전을 모르면 실제 영향은 단정하지 않습니다.

## 아직 결정하지 않은 것

- 기본 시각·주기·분량, 주간 실행 요일, 기준 시간대와 최초 소스 목록
- 오늘 재생성 전 회차의 열람 여부, 같은 날 여러 회차의 구분 방식
- 설정의 주기·분량 변경 적용 시점, 즉시 생성과 예약 생성이 겹칠 때 처리
- 같은 소식의 판별·중복 처리, 게시일 누락, 삭제된 원문 처리
- AI 모델, 로컬 LLM 또는 외부 API 선택
- 상세 데이터 구조, DB·기술 스택, 실행 일정과 실패·재시도 구조
- 배포 여부와 환경: 혼자 사용할 방법을 먼저 정하고 필요할 때 결정

다음은 위 기능을 기준으로 데이터 관계·보관 방식을 구체화하고, 소수의 실제 자료로 빠진 정보를 확인하는 작업입니다. 수집 기능 구현이나 DB 선택을 먼저 시작하지 않습니다.
